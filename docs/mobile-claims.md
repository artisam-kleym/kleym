## Connection and privacy

Freighter Mobile uses WalletConnect v2, rather than the browser extension API. On Android/iPhone/iPad browsers Kleym shows **Connect Freighter on phone** without the desktop **Connect wallet** button. Desktop browsers show only extension connection, even at a narrow window width; there is no phone option before or after desktop connection. Phone connections require `WALLETCONNECT_PROJECT_ID`; an unconfigured deployment displays an unavailable phone button and setup guidance instead of offering an unusable desktop connection.

1. Open your private claim URL in the Android browser and keep that tab open.
2. Select **Connect Freighter on phone**. Kleym prepares a pairing and tries to open the installed app directly. The verified route for Freighter v1.25.28 is `freighterwallet://wc-redirect?uri=<encoded pairing URI>`.
3. In Freighter select the deployment's Testnet or Mainnet and approve the connection. If the browser requires another tap, use **Open Freighter** on the pairing screen. Manual copying is inside **Freighter did not open?** as a fallback; open Freighter's QR scanner and paste the code only if direct opening does not work.
4. Return to the same browser tab. The page now says **Freighter connected. Your funds have not been claimed yet.** Review the displayed destination, then select **Claim**. Connection approval is wallet access, not a funds transfer.
5. If Kleym needs permission to create a sponsored USDC trustline, it publishes the exact signing request, then tries to reopen Freighter. Review/approve the transaction there and return to the tab. **Open Freighter to approve** retries app opening without another signing/claim request. This reopening link contains no pairing URI, claim URL, secret, session topic or XDR. An existing correct trustline needs no recipient signature and may complete without a wallet approval screen.
6. Wait for Kleym's confirmed receipt and independently verify the public transaction hash.

The pairing code is not your claim URL. It contains WalletConnect session capability data: keep it private and never send it to another person. The app-opening link carries only that validated pairing URI, not your private claim URL, fragment or recovery phrase. Opening the claim page does not contact WalletConnect or a wallet directory. Only the connection button starts the SDK. Application scripts/fonts stay same-origin; the explicit connection permits the WalletConnect relay and its isolated origin-attestation frame. Metadata contains only the site's origin, never the private URL, link key or recovery phrase. SDK telemetry is disabled and session storage is in memory. Wallet requests contain only public transaction XDR, using `stellar_signXDR`; the wallet never submits Kleym transactions.

Kleym checks session chain, signing permission, expiry and account before preparing/signing; session updates and disconnects require reconnection. Returned transactions must retain the reviewed hash and existing signatures and contain the selected recipient's valid signature under the expected network passphrase. Server verification and exact-hash recovery remain authoritative.

Switching apps should retain the tab. Android may discard it under memory pressure. If it reloads, reopen the original private claim URL from your own saved message/export; the fragment was deliberately removed and no key is saved in browser storage. Do not repeat funding. Existing ledger state and transaction journals govern retries.

Configure a user-owned project at [WalletConnect Dashboard](https://dashboard.walletconnect.com/), allowlist the exact generated HTTPS origin, and set its public project ID in Railway. See [hosting setup](railway.md).

Record Android/Freighter version, deployed source version, network, public account addresses and public transaction hashes. Test a fresh recipient with no USDC trustline and an existing recipient with the exact trustline. Verify exact USDC credit, zero recipient XLM top-up, sponsor fee/reserve accounting, later-ledger TX2, temporary account removal and no duplicate payment on retry. Also decline a prompt, switch network/account and return after app backgrounding. Local SDK/session fixtures do not establish these device results.
